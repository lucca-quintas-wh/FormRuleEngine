data-required-when · data-disabled-when

Dois plugins quase idênticos por dentro: avaliam a condição e alternam um atributo no input. A diferença que importa está em onde o atributo mora.

Dependências: nenhuma

A armadilha do wrapper — leia antes de escrever a primeira regra.

Estes plugins encontram o campo com element.querySelector('input, select, textarea'): procuram dentro do elemento e nunca consideram o próprio elemento. Colocar data-required-when direto no <input> falha em silêncio — sem erro, sem aviso no console, o campo simplesmente nunca fica obrigatório. 

<!-- NÃO funciona -->
<input name="Cnpj" data-required-when='{"TipoPessoa":"J"}'>

<!-- funciona: o atributo vai no wrapper -->
<div data-required-when='{"TipoPessoa":"J"}'>
  <input name="Cnpj">
</div>

data-visible-when é a exceção — age no próprio elemento —, o que torna a armadilha pior: o primeiro plugin que a maioria experimenta funciona nos dois lugares, e a expectativa se forma errada. Corrigir o findInput() para tolerar os dois casos está no roadmap.

1. Obrigatoriedade condicional

Quando a condição é verdadeira, o plugin põe required no input e as classes ilu-input--required e required. Se existir um rótulo com a classe ilu-form-label dentro do wrapper, ele também ganha ilu-form-label--required — é assim que o asterisco aparece (o CSS é seu; veja o bloco "contrato visual" em assets/demo.css).

2. A mesma regra escrita errado

Abaixo, o atributo está no próprio input. Nada acontece — nem erro, nem asterisco. Deixamos o caso aqui de propósito, para você reconhecer o sintoma.

3. Habilitação condicional

data-disabled-when alterna o atributo disabled, adiciona ilu-input--disabled no input e ilu-form-field--disabled + form-rule-disabled no wrapper — as classes existem para você estilizar o campo inteiro, não só a caixa de texto.

Efeito colateral útil: campo disabled não é enviado no submit. Isso o torna a forma mais limpa de garantir que um ramo inaplicável não chegue ao servidor — mais confiável do que esconder, já que campo oculto continua sendo serializado.

4. Obrigatório e visível: a dupla que anda junta

Repetir a condição nos dois atributos é o padrão, e é intencional: são regras independentes e nada obriga que coincidam. Um campo pode ser visível e opcional, ou obrigatório dentro de um bloco que só aparece em outro contexto.

Obrigatório dentro de bloco oculto. Se um campo com required ficar escondido, a validação nativa do navegador trava o submit sem mostrar onde está o erro — o Chrome recusa focar um campo invisível. Por isso, sempre que um bloco condicional contiver campos obrigatórios, faça a obrigatoriedade depender da mesma condição da visibilidade (como acima) ou desabilite o bloco ao escondê-lo.

5. Depender de um campo calculado

Uma regra pode depender de um campo que outro plugin escreve. A engine dispara change ao gravar via setFieldValue(), então o encadeamento acontece sozinho — sem ordem de registro para acertar.
