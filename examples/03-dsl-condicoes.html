A gramática das condições

Uma só gramática para todos os data-*-when. Aprendida uma vez, vale para visibilidade, obrigatoriedade, máscara, AJAX, wizard — tudo. Ela vive em evaluateCondition(), no núcleo, e tem menos de 40 linhas.

Dependências: nenhuma

1. As cinco formas

FormaSignificado
{"Campo": "S"} Igualdade. Comparação estrita (===) contra o valor cru do campo, que é sempre string.
{"Campo": ["A","B"]} Pertence a. Verdadeiro se o valor do campo está na lista.
{"Campo": {"!=": "S"}} Forma com operador. A chave é o operador; o valor é o operando.
{"AND": [ … ]} Conjunção. Cada item é uma condição completa, e pode conter outro AND/OR.
{"OR": [ … ]} Disjunção, aninhável do mesmo jeito.

2. Operadores

OperadorComparaçãoExemplo
eqigualdade estrita (idêntico à forma curta){"Status":{"eq":"A"}}
!=diferença estrita{"Status":{"!=":"A"}}
> < >= <=numérica, via parseFloat nos dois lados{"Idade":{">=":18}}
regexnew RegExp(valor).test(campo){"Email":{"regex":"@empresa\\.com$"}}
eq_fieldcompara com outro campo; o operando é o nome dele{"Confirmacao":{"eq_field":"Senha"}}
neq_fieldidem, negado{"Destino":{"neq_field":"Origem"}}

eq_field/neq_field são o que permite escrever "confirmação igual à senha" ou "o tipo escolhido difere do já cotado" sem cair em JavaScript solto. Sem eles, toda comparação entre dois campos vira função à mão.

3. As duas armadilhas

Só a primeira chave do objeto é lida.

{"A":"1","B":"2"}     // avalia SÓ {"A":"1"} — B é ignorado em silêncio
{"AND":[{"A":"1"},{"B":"2"}]}   // o que você queria escrever

evaluateCondition() pega Object.entries(rules)[0] e descarta o resto. Não é um AND implícito. Decidir entre tratar como AND ou avisar no console é item aberto do roadmap.

Igualdade não converte tipo; comparadores numéricos convertem.

{"Quantidade": 1}          // FALSO: o campo vale "1" (string), e 1 !== "1"
{"Quantidade": "1"}        // certo
{"Quantidade": {">": 0}}   // funciona com número: passa por parseFloat

4. Como os campos são lidos

getFieldValue() normaliza por tipo de controle. Vale conhecer, porque a condição compara contra isto:

ControleValor lido
texto, select simples, textareafield.value (string)
checkbox"S" quando marcado (ou o value do campo, se houver); "N" quando desmarcado
radioo value do que estiver marcado, ou null
select multiplearray de valores selecionados
campo inexistentenull

A consequência prática do select multiple: comparar por igualdade contra um array quase nunca dá certo. Para "selecionou o item X", o caminho hoje é um campo auxiliar preenchido por computed ou por set_value.

5. Parâmetros do formulário

form_param_<nome> referencia um parâmetro do formulário inteiro, não um campo de dados — modo de edição, origem da chamada, perfil do usuário. A busca é feita por [name="form_param_x"] e, se não achar, por [name="__form_param_x"]; a convenção é o hidden com dois underscores. Mudar um deles reavalia todas as regras do formulário, não só as dependentes.

7. Como as dependências são descobertas

No registro do plugin, a engine faz JSON.parse da regra e chama extractDependencies(), que devolve os nomes de campo citados. Com isso monta um Map de campo → elementos que dependem dele. No change, só esses elementos são reavaliados.

O helper padrão (extractFieldNames) desce por AND/ OR e ignora chaves que não são nome de campo — label, mask, options, rule, params, class. É por isso que os formatos "lista de regras com metadado" (usados por label_when, mask_when, validate_when) funcionam sem configuração extra.

Consequência: uma condição construída dinamicamente depois do registro não entra no mapa. Elementos criados em runtime precisam de engine.addElement(el, 'visible') — é exatamente o que o plugin repeater-init faz para cada linha nova.
